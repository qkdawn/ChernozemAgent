# 黑土农情 Agent 设计

> 当前目标：让用户选择一个地块和一项农情任务后，得到可理解、可定位、可行动的结果。

> 规划跨期追踪、巡田复核、专业发布和持续预警时，读取[工具体系完整设计](farm-agent-tool-system-plan.md)，以确定目标边界、模块所有权和实施验收；其中新增能力尚待实施。

## 1. 第一性原理

产品同时提供纯对话和功能工作流。对话用于理解、解释和追问，功能工作流用于完成一次农田任务：

```text
用户目标 -> 选择正确能力 -> 调用确定性工具 -> 理解结果 -> 给出下一步行动
```

系统只保留四个核心概念：

- **Data**：已经获取并登记的事实，包括影像、天气、地形、土壤和地块信息。
- **Tool**：把数据处理成稳定的专业结果，不依赖模型计算遥感指标。
- **Knowledge**：提供有来源的农学、区域和方法背景，帮助解释工具结果，不制造地块事实。
- **Workflow**：规定一项功能按什么顺序调用工具、如何处理缺口、如何形成结构化结果。

数据层回答“观测到了什么”，工具层回答“算出了什么”，知识层回答“如何理解以及依据来自哪里”，Workflow 层回答“为了完成用户任务，接下来做什么”。

### 1.1 运行架构

```text
用户工作区
├── AI 对话 -> 对话工具门面（读取、规划、确认后启动 Workflow）
└── 功能面板 -> 固定农情 Workflow -> 受控领域工具 -> 结构化结果

共享底层
├── PostgreSQL：地块、任务、消息、结果与运行轨迹
├── Artifacts：地图和分析产物
├── GraphRAG：按需提供农学解释上下文
└── 独立数据采集：Sentinel、DEM、天气和土壤
```

数据采集与对话、功能工作流平行运行。对话 Agent 不直接读取原始资产或调用底层分析工具，只能通过受控的对话工具门面读取已发布结果、规划 Workflow，并在用户确认后启动任务；功能工具只读取已登记资产。`get_field_context` 按当前边界版本确定性读取地块档案、数据状态和最近三项任务，原始边界与资产不会进入对话结果；`plan_workflow` 返回待确认计划，确认后复用现有任务创建入口启动 Workflow。`get_workflow_status` 回答当前地块最新匹配任务的状态；`get_task_result` 从同一任务范围读取摘要、地图位置、依据、限制或行动。这些只读查询都不会调用模型或创建任务，结果继续使用普通对话文字。`record_scouting_note` 先生成候选草稿，再复用地图点选和巡田表单完成确认；对话本身不会静默写入。Workflow 完成首轮计算后，文档分析模型通过 Codex 原生 MCP 按需读取本任务成果、检索农学原文，或调用当前任务已注册的证据计算工具，再比较、解释并撰写完整正文。具体发布契约见第 7 节。MCP 不提供 SQL、文件、Shell 或供应商 API 的旁路。

## 2. 一个对话 Agent，四个任务域

首期只有一个面向用户的 **黑土农情对话 Agent**。“功能”面板按用户任务收敛为长势、水氮管理、积水和霜冻四个一级入口，不按算法或产物平铺。它们是独立、确定、可重放的工作流，不是四个 Agent，也不由对话静默触发；对话 Agent 可以在计划并获得用户确认后启动其中一条 Workflow。

水氮管理内部包含“诊断”和“施氮方案”两个二级动作。诊断负责定位异常、组织水分与氮素证据并生成核查方向；施氮方案基于已有长势分区由用户填写各区用量，保存为 `needs_review` 候选方案。二者在产品上属于同一管理任务域，但执行契约保持分离：诊断不会自动生成施肥剂量，候选方案也不能绕过农艺复核。

用户选择功能时，服务端按任务目标执行一项 Workflow：

| Workflow | 用户任务 | 核心业务工具 |
| --- | --- | --- |
| 关键生育期长势监测 | 当前处于什么生育期、长势如何、哪里存在差异 | `assess_growth_status` |
| 水氮协同诊断 | 哪些区域可能受水分或氮素限制 | `assess_water_nitrogen_evidence` |
| 农田积水灾害识别 | 降雨后哪里疑似积水、影响多大 | `detect_waterlogging` |
| 霜冻风险提前预警 | 什么时候可能发生霜冻、哪里风险更高 | `assess_frost_risk` |

任务目标在创建任务时已经确定，不让模型重新猜测。一个任务只运行一个 Workflow，首轮计算按代码声明的固定顺序执行；随后的模型分析允许按问题补调任务内证据工具。它不改变原任务目标，也不把固定首轮链路称作自主规划。

任务时间范围同样在创建时固定。`last_30_days` 和 `this_season` 由服务端解析为 UTC 起止时间；`custom` 必须提供明确起止时间。首轮与补充工具均只读取当前地块边界下已登记的采集产物；观测窗口、季内比较基线或雷达/天气支持窗口由领域模块解析。任务 `timeRange` 与各成果的实际范围同时保留，窗口外观测必须说明其比较或背景角色。

## 3. Workflow 层

Workflow 是短小、稳定、由代码执行的工作规程，不保存算法、阈值、数据源配置或供应商细节。

每项 Workflow 只需要说明五件事：

1. 当前任务要回答什么问题；
2. 哪些工具可以帮助完成任务；
3. 缺少必要输入时询问什么；
4. 工具无法形成结论时如何停止；
5. 最终结果如何组织。

统一执行过程：

```text
读取任务上下文
-> 调用当前 Workflow 所需的工具
-> 根据工具状态继续或停止
-> 输出结论、地图、依据和下一步行动
```

Workflow 不进行以下工作：

- 不下载数据；
- 不选择波段、轨道、坐标系或算法阈值；
- 不执行 Python、SQL、文件读写或任意网络请求；
- 不把缺失数据补成正常值；
- 不把风险预测描述为已经发生的灾害。

## 4. 工具层

工具的自顶向下设计、四条 Workflow 的步骤图以及十个工具的逐项职责，统一见 [agent-tool-design.md](agent-tool-design.md)。本节只保留运行时边界和当前实现摘要，避免在多个文档复制工具定义。

工具只做两件事：生成任务分析结果，或基于已有分析结果完成一项业务判断。裁剪、配准、指标、统计、分区、产物写入和资产选择都留在工具内部，不注册为 Agent 工具。

这里的“空间工具”指 Agent 可调用、能回答一个农田空间问题的领域工具，不是前端图层开关，也不是 GIS 算子集合。空间能力固定分为三层：

| 层 | 由谁使用 | 内容 |
| --- | --- | --- |
| Agent 工具 | Workflow / Agent | 光学田况、雷达变化、地形易发性、积水识别等具备农情语义的受控工具 |
| 工具内部能力 | 工具实现 | 地块裁剪、投影归一、时间与分辨率对齐、质量门、统计、空间相交、分区和产物登记 |
| 地图展示 | 前端 | 展示工具已经发布的图层、分区、巡田点和来源，不参与分析决策 |

不再为 Agent 单独注册 `clip_raster`、`reproject`、`resample`、`intersect_layers`、`publish_artifact` 或任意几何运算。把这些步骤暴露给模型会要求它理解坐标系、路径、中间产物和执行顺序；这些信息由拥有完整上下文的分析工具一次处理。

### 4.1 Workflow 受控工具

证据工具：

| 工具 | 输出 |
| --- | --- |
| `analyze_optical_condition` | 按观测日期归并已采集 Sentinel-2 资产，输出 NDVI、NDRE、RECI、MSAVI、NDMI、NDWI 图层、可用时相、日期变化和田内光学差异 |
| `analyze_radar_change` | 雷达后向散射变化、前后时相和变化区 |
| `analyze_weather_event` | 降雨、低温或积温事件及其时间窗口 |
| `analyze_terrain_susceptibility` | 低洼、坡度和相对地形易发区 |
| `get_soil_background` | 地块级 SoilGrids 属性和尺度限制 |
| `estimate_crop_stage` | 基于播期、积温、品种和光学辅助的阶段区间 |

其中真正生成或读取田内空间结果的证据工具只有三类：

- `analyze_optical_condition`：单期观测、跨期比较和田内相对差异；
- `analyze_radar_change`：同轨可比时相和雷达变化区；
- `analyze_terrain_susceptibility`：静态高程、坡度与低洼易发区。

天气与土壤不是田内空间工具。`analyze_weather_event` 只提供时间事件，`get_soil_background` 只提供地块级背景；二者可以参与业务判断，但不能生成伪高分辨率分区。

业务工具：

| 工具 | 输出 |
| --- | --- |
| `assess_growth_status` | 生育期长势、变化、差异区和核查动作 |
| `assess_water_nitrogen_evidence` | 田况观测、巡田优先级、同期现场记录及多源复核动作 |
| `detect_waterlogging` | 疑似积水区、面积、观测日期和核查优先级 |
| `assess_frost_risk` | 预报风险窗口、地形关注区和防护动作 |

Workflow 直接调用工具时输入为 `{ taskId: string }`。文档分析的 MCP 会话已在服务端绑定任务，模型调用证据计算时输入为空对象，知识检索只输入 `{ query }`，不能覆盖 taskId 或地块。

Workflow 按能力声明依次调用多个分析工具。业务工具不接收前序结果引用；服务端按当前任务和结果类型读取本次执行刚保存的前序结果，并在必需结果缺失时返回明确状态。

### 4.2 任务分析结果

工具把完整结果登记到当前任务的分析结果空间。文档模型先收到成果目录，再按结果 ID 和 JSON Pointer 读取实际数据：

```text
首轮工具 -> 持久化领域结果
任务 + 成果目录 -> Codex 原生 task_evidence MCP
                 -> 读取成果 / 农学原文 / 补充计算
                 -> 新成果先保存，再供读取和引用
                 -> 模型文档 + 原任务全部成果
```

结果 ID 是稳定引用，不是文件路径。模型只能读取当前任务、地块和边界版本的成果；无权限或不存在的 ID 被拒绝。MCP 不返回 envelope 中的 summary、findings、nextActions 或 limitations，避免其预写措辞直接进入模型上下文。现有部分业务 assessment payload 仍含解释字段，此轮没有将所有确定性业务工具改为纯观测契约。

任务文档和 `AnalysisResult<T>` 分别持久化到 PostgreSQL。任务文档保存解析后的时间范围、状态、结果摘要、地图引用、来源、限制和下一步动作；API 重启后仍可通过任务 ID 读取。运行时栅格与 GeoJSON 继续保存在 `runtime/artifacts`，数据库只保存引用。

前端“分析记录”按当前主体倒序读取已持久化任务。重新打开历史任务只读取原任务文档和 `AnalysisResult<T>`，恢复当时的结构化结果、来源与地图产物，不重新执行工具，也不把历史任务包装成新结论。

### 4.3 最小证据矩阵

这是业务工具的代码配置，不由模型决定：

| Skill | 必需结果 | 可选或辅助结果 | 结果不足时 |
| --- | --- | --- | --- |
| 长势监测 | 可用 `optical_condition` | `crop_stage` | 缺光学观测时 `needs_data`；缺播期时仍交付田况和空间差异，但生育期解释为 `partial` |
| 水氮排查 | 可用 `optical_condition`；时间及质量口径见工具契约 | 同日差异、跨期变化、雷达/低洼几何交集、可选同期现场对照 | 工具交付测量与对齐状态；Agent 比较后解释，不因缺巡田记录阻断分析；处方另行进入专业复核 |
| 积水识别 | 合格灾前/灾后 `radar_change` | 关联 `weather_event`、`terrain_susceptibility` | 缺可比雷达时 `needs_data`；有雷达变化但缺连续降雨时只交付变化区，不升级为积水判断 |
| 霜冻预警 | 有效 `weather_event` | `crop_stage`、`terrain_susceptibility` | 缺预报时 `needs_data`；缺播期时仍交付低温过程和低洼关注区，但风险等级保持待判定 |

“可选”不等于可以忽略影响。工具必须在 `sources` 和 `limitations` 中说明少了什么、结论缩小到什么范围。

### 4.4 统一结果

`AnalysisResult<T>` 是工具返回和后台保存的唯一结果类型，定义位于 `packages/contracts/src/index.ts`。文档只规定语义，不再复制第二份 TypeScript 接口。

`succeeded` 表示达到该工具的完成条件；`partial` 表示仍有可交付但范围受限的结果；`needs_input` 是用户或业务资料缺失；`needs_data` 是当前采集不能支撑判断；`needs_review` 只用于需要专业复核的高风险结果；`failed` 是系统执行失败。每个 finding 必须列出来源和日期，不能只返回无来源分数或颜色。

光学结果的 `result` 只保留当前时相、可用时相序列、日期间变化和当前田内分区：

```text
{
  current: { observationDate, metrics, quality },
  observations: [{ observationDate, metrics, quality }],
  changes: [{ fromDate, toDate, ndviDelta, ndreDelta, reciDelta, msaviDelta, ndmiDelta, ndwiDelta }],
  zones: [...]
}
```

工具读取任务时间范围内同一地块、同一边界版本的采集历史，并按日期要求同一日期、同一场景的 10 米光谱、20 米光谱和 SCL 完整到齐；不会把不同日期或不同场景的波段拼成一景。只有一个可用日期时仍返回当前状态和地图，但状态为 `partial`，并明确“时相不足，不能判断历史变化”。日期间趋势使用版本化的 `MEANINGFUL_NDVI_CHANGE = 0.03` 工程阈值，后续用东北玉米样本校准；它不等于产量预测或农事处方。

地块不在影像覆盖内返回 `no_field_coverage`；全部像元受云影响返回 `cloud_contaminated`；仍有部分有效像元时保留结果并标记 `partial`。三者不能统一写成“无数据”。

底层分析工具只返回观测、变化、质量和限制，不生成施肥、灌溉、防护或巡查动作。业务工具才生成结论和下一步行动。

### 4.5 四项业务规则

- `assess_growth_status`：以同一地块的合格光学时序为主，输出阶段、长势分级、变化日期和田内相对差异；没有跨地块基准时不做产量排名。
- `assess_water_nitrogen_evidence`：地块田况工作区独立展示真实日期、原图、指数和季内时序，不创建 Agent 任务。水氮任务用同日 NDVI、NDRE/RECI 与 NDMI/NDWI 定位并描述光谱差异，但不直接分配水氮原因；水分方向需空间对齐雷达、强降雨与低洼组合或同期现场墒情支持，氮素方向需同期现场叶色对照并排除明显水分和病虫害线索。巡田记录只有用户明确选择且与影像相差不超过 3 天时进入结果。未实际改变方向的数据不进入业务来源；没有本地验证模型时不输出水氮确诊和处方。

产品借鉴 OneSoil 的地图工作流：先呈现真实观测日期、标准指数、田内对比图层和季内时序，再允许用户在任意关注位置添加带坐标的巡田记录。自由巡田记录不改造成强制 `0/2` 流程。稳定生产力分区必须有多个可比种植季；单季单期 NDVI 只能生成当期相对长势管理区，不能称为长期生产力、缺氮或推荐施氮分区。

“水氮管理”内提供独立的“施氮方案”子工作流。它不属于水氮诊断工具，也不由 Agent 自动决定剂量：用户选择一个已有 NDVI 分区日期，系统使用 `ndvi-quantile-connected-v2` 检查有效像元 NDVI 的 P90-P10 稳健极差；达到 0.05 时才形成低、中、高三个相对长势候选管理区，并执行邻域平滑、碎斑吸收和连通区矢量化。差异不足时全田只标记为中等区，不开放处方创建；旧版 3×3 几何网格不再使用。用户填写肥料、含氮率、常规用量和各区产品施用量。服务端统一计算各区面积、肥料总量、折纯氮量以及相对均匀施用的增减量。保存结果固定为 `needs_review` 候选方案，可预览地图并导出 GeoJSON；正式农机格式、对照条带、跨季稳定生产力区、产量图反馈和推荐剂量模型需在后续田间校准后实现。SoilGrids 不参与田内分区。

分析记录默认只列最近 20 条并按四项能力筛选。仍保留在数据库中的早期水氮试验任务标记为“历史版本”，打开时不再展示已停用的单期归因和候选区，只提供按当前方法重新分析的入口。

巡田记录在地块详情中拥有独立入口，并作为常驻点位叠加在地图上。退出某次分析后记录仍可浏览和定位；从记录发起后续分析时，只把用户选中的记录 ID 传入任务。它不是遥感数据源，也不因新建任务而复制或自动归因。
- `detect_waterlogging`：必须使用同轨道条件可比的灾前/灾后 Sentinel-1 观测；雷达变化是疑似积水证据，天气负责关联降雨，DEM 只负责巡查排序。用户从某个雷达日期发起任务时，该日期仍是任务目标日，工具内部自动向前读取最多 24 天的雷达证据窗口以寻找同轨基线，不要求用户手工选择第二期影像。
- `assess_frost_risk`：始终使用最新预报及其未来有效时间、生育期敏感性和 DEM 易发区；不继承地图历史观测日期，也不接受历史日期范围。输出预测风险，不写成已发生霜冻，也不把粗分辨率预报下推成田内精准温度。

`estimate_crop_stage` 的基温、积温起算、阶段阈值、品种修正和不确定区间必须放在版本化配置中；缺少播种日期、日期格式无效或播种日期晚于参考观测日时返回 `needs_input`，不能仅凭一幅影像命名生育期，也不能把未来播期静默归为出苗期。

## 5. 知识层

知识库与地块业务数据库共用 PostgreSQL，但在逻辑上是独立领域。它不保存实时地块观测，而是保存东北黑土地玉米生产中可引用、可更新和可追溯的知识。

### 5.1 范围

知识范围按“一个地区、一个作物、四项任务”收敛：

- **地区**：东北黑土区，覆盖辽宁、吉林、黑龙江和内蒙古东部；首期优先辽宁铁岭及邻近积温带；
- **作物**：露地春玉米，包含播种、出苗、拔节、抽雄、吐丝、灌浆和成熟等阶段；
- **农学问题**：长势、水分与氮素相关异常、涝害、低温与霜冻；
- **方法知识**：光学、雷达、天气、地形和土壤背景如何支持或限制上述判断；
- **现场知识**：应观察什么、到哪里核查、哪些现象可以支持或排除一种解释。

不收录与东北春玉米任务无关的通用农业百科、农资营销材料和没有出处的网络问答。其他作物或地区以后建立独立范围，不混入当前图谱。

### 5.2 来源

知识库按来源类型管理，不把搜索结果直接视为知识：

| 来源 | 主要用途 | 入库要求 |
| --- | --- | --- |
| 国家、行业和地方标准 | 术语、阶段定义、调查方法和技术边界 | 保存标准号、发布机构、版本和适用范围 |
| 农业主管部门与农技推广材料 | 东北春玉米生产历、灾害应对和现场核查 | 保存发布单位、地区、发布日期和原文位置 |
| 同行评议论文与综述 | 生育期、积温、遥感响应、胁迫机理和方法限制 | 保存作者、题名、期刊、年份、DOI 和具体页段 |
| 学术专著、教材和地方志 | 黑土、玉米生理、栽培制度和区域背景 | 保存 ISBN、版本、章节和页码 |
| 农业试验站与项目专家材料 | 铁岭本地品种、播期、灾情和核查经验 | 标明试验地点、年份、材料提供者和适用边界 |
| 数据产品与算法官方文档 | Sentinel、ERA5-Land、IFS、DEM、SoilGrids 的指标和分辨率限制 | 保存产品版本、官方链接和生效日期 |

公开或已授权材料可以保存全文。受版权保护的书籍和论文只保存依法取得的原文、允许使用的片段，或者带页码的项目笔记；不把来源不明的整本 PDF 放入对象存储。模型生成内容不能作为来源，只能作为待人工确认的索引草稿。

每份材料至少记录：标题、来源类型、作者或发布机构、年份、DOI/ISBN/标准号、适用地区、作物、品种或熟期、生育期、任务能力、许可状态、原文位置和版本。相互冲突的材料分别保留，不由索引阶段擅自合并成唯一结论。

### 5.3 GraphRAG 图谱

本项目使用 Microsoft GraphRAG 官方 Python 管线，不自建一套兼容表。GraphRAG 会从文本抽取 entities 和 relationships，进行 community detection，生成 community reports，并生成文本、实体和报告向量；claims 只有在固定配置开启后才生成。默认索引产物是 Parquet，向量存储默认是 LanceDB。

项目数据库只保存来源和索引运行元数据：

```text
knowledge_source
  论文、书籍、标准或地方材料的书目信息、许可、适用地区、原文引用和版本

knowledge_index_run
  GraphRAG 版本、配置哈希、prompt 版本、模型、输入清单、Parquet 输出和向量库引用

knowledge_index_run_source
  一次索引运行包含哪些已发布来源
```

GraphRAG 的派生表不复制到业务 PostgreSQL，而保存在专用 workspace 或对象存储中：

```text
documents / text_units / entities / relationships / claims
communities / community_reports
Parquet 输出 + LanceDB 向量库 + GraphRAG cache
```

每个输入文档必须把地区、作物、生育期、能力、来源标识和页码/章节作为原始字段或前置 metadata 写入。这样 Local Search 返回的 text unit 能回到具体来源，而不是只返回模型生成的摘要。

首期只使用 GraphRAG Local Search。Global Search 适合全库主题总结，DRIFT Search 会增加查询成本，暂不接入。`extract_claims` 需要单独调 prompt 和成本，首期只对来源充分、问题明确的材料开启。

GraphRAG 官方仓库明确提示索引会消耗较多 LLM 资源，且项目处于 maintenance mode。因此 Python worker 必须锁定版本、保留配置和 prompt，索引失败不能影响已有农情分析结果。

### 5.4 入库与更新

```text
登记来源与使用权限
-> 写入 GraphRAG input 文件及 metadata
-> 运行固定版本的 GraphRAG index
-> 检查 text_units、claims 和 citations 可回溯到原文
-> 登记 Parquet、LanceDB 和配置版本
-> 发布索引运行
```

原文更新时生成新版本，不覆盖旧版本；历史任务继续保留当时引用的索引运行。算法阈值、公式和质量规则不只存在于 GraphRAG 文本中，而是放在版本化代码或结构化配置中，并反向链接支持它的知识来源。

### 5.5 Agent 如何使用

知识检索是服务端只读能力，不属于数据采集，也不参与遥感计算：

```ts
search_agronomy_knowledge(input:
  | { taskId: string; query: string }
  | { fieldId: string; query: string }
): {
  status: "succeeded" | "no_matches" | "unavailable";
  indexRunRef: string | null;
  answer: string | null;
  matches: Array<{
    excerpt: string;
    textUnitIds: string[];
    relatedEntities: string[];
    applicability: { regions: string[]; crops: string[]; stages: string[] };
    citation: { title: string; locator: string; sourceUrl: string | null; version: string };
  }>;
  limitations: string[];
  error: { code: string; message: string; retryable: boolean } | null;
}
```

调用方必须在 `taskId` 和 `fieldId` 中只提供一个。任务范围自动固定为玉米、任务地区和当前 Workflow，只返回适用于该能力或通用的来源；地块范围先校验组织与玉米作物，再读取最新已发布索引，用于普通对话中的一般农学解释，不把任何知识写成当前地块事实。模型不能指定 workspace、索引版本、文件路径、图查询或 SQL。成功结果必须带 text unit、来源定位和索引运行引用。

服务端只在以下情况调用知识检索，并把结果作为只读上下文交给对话 Agent：

1. 解释业务工具已经确认的观测或诊断；
2. 回答用户对生育期、指标、可能原因和现场核查方法的追问；
3. 为下一步行动补充适用于当前地区和生育期的依据。
4. 在未绑定任务的地块对话中回答东北春玉米的一般农学问题。

知识不能覆盖工具结果，不能把一般规律写成当前地块事实，也不能补造缺失观测。检索不到适用材料时，Agent 只陈述工具事实和数据限制。

### 5.6 首批知识包

第一阶段只建设支撑长势监测的最小知识包。GraphRAG 索引作为独立作业，不阻塞确定性长势结果：

1. 东北春玉米生育期定义、播期和积温方法；
2. 辽宁北部或铁岭主要熟期类型与生育进程材料；
3. 玉米冠层光学时序与关键生育期变化的论文或综述；
4. Sentinel-2 红边、植被指数和云影响的官方方法说明；
5. 生育期和长势现场核查表。

水氮、积水和霜冻知识包随对应业务工具开发再加入。首批材料的完成标准不是文档数量，而是能够对真实长势任务中的“阶段依据、变化解释、方法限制、现场核查”分别返回带页码或章节的出处。

## 6. Agent 运行过程

```text
创建任务
-> 服务端固定地块、时段和 Workflow
-> Workflow 按固定顺序调用分析工具并获得摘要与来源日期
-> 业务判断工具按 taskId 读取本次前序分析结果并形成结果
-> 服务端保存结论、依据和行动
-> 前端展示地图、依据和行动
-> 用户围绕本次任务继续追问
```

任务状态保持简单：

- `planned`：任务已创建；
- `running`：Workflow 或工具正在执行；
- `needs_input`：缺少播种日期等用户可以补充的信息；
- `needs_data`：当前数据不能支撑分析；
- `needs_review`：高风险结果等待专业复核；
- `partial`：已有范围受限但可交付的结果；
- `completed`：已经形成可交付结果；
- `failed`：系统执行失败。

工具状态和任务状态不混用。工具 `succeeded` 后任务仍可能继续调用其他工具；只有业务结果已经保存并满足当前 Workflow 的完成条件，任务才进入 `completed` 或 `partial`。

## 7. 用户最终看到什么

一次功能任务固定呈现：

1. 当前结论；
2. 地块内的空间分布；
3. 关键时间或变化；
4. 使用的数据与日期；
5. 下一步现场行动；
6. 针对当前结果的追问入口。

报告只是可选导出。Agent 的完成标准是用户已经知道“发生了什么、发生在哪里、依据是什么、下一步做什么”。

首轮任务计算完成后，`analysis-brief-writer.ts` 将当前任务和成果目录交给 Codex，而非一次性注入完整结果正文。模型可以比较结果、解释原因、组织正文和提出非处方性的核查建议，不再只润色四个字段，也不受汉字白名单、原文词频或固定七章模板限制：

```text
headline     一句明确结论
overview     当前状态、空间范围和关键数值
reasoning    证据如何支持当前判断
uncertainty  只说明实际改变本次结论的未知项
document     模型按实际问题组织的完整分析正文
evidence     主要判断、结果 ID 和 result 内的 JSON Pointer
actions      有具体对象、目的和操作的下一步
```

`AnalysisResult` 仍是地块事实来源。MCP 读取复用已保存的 result、范围、来源和参数，不另建 facts memo。发布门校验任务/地块/边界范围、JSON 结构、结果字段引用和分区关联，要求引用字段已实际读取且非空；来源日期由后端按实际引用还原。知识引用指向保存的原文片段，显示出处、定位和版本，与地块观测日期分开。它不再比较字词是否与底稿相同。引用可解析只证明可追溯，不能证明自然语言里的每个数字、方向、因果或诊断正确；这些仍需主张级评测与专家案例审查，不能把接口测试当成农业有效性验证。

`generation` 记录 `deterministic / model_generated`、生成时间、provider、model ID、prompt 版本和失败原因。模型未配置、坏 JSON、引用越界、超时或模型错误时保留简短计算摘要，界面明确标识“AI 解读未生成”；不再用七章硬编码正文伪装生成成功。模型声明 `reviewRequired`，或发布门发现明确的施肥、灌溉、用药执行建议时，任务进入 `needs_review`；原工具要求的专业复核不会被模型解除。文本规则覆盖常见执行用语，不保证识别所有自然语言处方，不能替代处方模块的独立专业发布流程。

现阶段实现为“固定首轮计算 + 原生 MCP 按需调查与文档生成”。读取、补算、知识检索和成果保留的工程契约已通过集成测试；真实模型生成质量尚待可达服务验收。文档会话 MCP 绑定 loopback 随机端口和一次性令牌，生成结束即关闭。Shell、文件编辑、任意网络与其他 MCP 不属于此会话能力。`AnalysisBriefPublication` 同时返回正文与新增计算/知识成果，任务保存使用同一个发布结果。

当前验收进展及剩余工作见 [agent-workflow-optimization.md](agent-workflow-optimization.md)；[原审查记录](agent-workflow-review.md)描述的是 2026-10-24 的改造前状态。

### 7.1 前端信息密度

- 默认只呈现完成当前任务所需的结论、动作和状态；解释性文案只在消除歧义、说明数据影响或支持失败恢复时出现。
- 同一信息不在入口按钮、面板标题、选中项和辅助说明中重复。入口使用熟悉图标和短标签，面板内部直接进入可操作内容。
- 地图控件保持短标签和紧凑层级。图层菜单保留来源、日期、指标、选中状态和必要署名，不重复描述当前底图或控件用途。
- 空状态用一个短句说明当前状态；只有用户可以立即补救时才附带一个明确动作。
- 专业数据、质量、参数和执行轨迹通过按需展开呈现，不长期占据地图主工作区。

前端地图图层固定分为四组。它只是 Agent 工具产物的展示面板，不命名为“空间工具”，也不把所有来源平铺成工具市场：

1. **底图层**：卫星底图只提供地表背景；
2. **空间对象层**：地块边界、当前任务结果、巡田记录和施氮候选分区可以分别开关；
3. **农情观测层**：按来源、日期和指标选择 Sentinel-2 光学、Sentinel-1 雷达或 DEM 地形的一层栅格；
4. **地图动作层**：回到当前农田、定位记录和进入现场核查，动作不伪装成数据图层。

天气与土壤不直接伪装成田内栅格：天气用时间图表表达，SoilGrids 用地块级背景表达尺度和限制。没有任务、巡田记录或施氮分区时，对应对象保持禁用，不用空图层占位。地图默认只显示卫星底图、地块边界和当前任务结果；用户主动选择观测图层后才覆盖底图。

## 8. 第一阶段实现

当前代码已完成四项能力的首版纵向切片：任务与 `AnalysisResult` 持久化、任务时间范围、Sentinel-2 多时相光学处理、生育期估计、同轨 Sentinel-1 双时相采集与积水识别、天气/地形霜冻风险、水氮相关田况筛查及可选现场记录复核均已接入 API。四类结果都在 Workflow 面板内直接呈现任务事实：长势展示有效观测、覆盖率、趋势和偏弱区；水氮展示田内差异、时相变化、原因证据层级和同期现场对照；积水展示雷达间隔与覆盖、显著变化面积、降雨门槛与事件、疑似影响面积；霜冻展示风险窗口、最低温与持续时间、生育期敏感性、预报批次与覆盖率。最新田内分区只绑定生成它的观测日期。任务读取同一地块、同一边界版本且位于任务时间范围内的采集历史；缺少完整光学资产、可比雷达对或有效天气预报时返回明确的 `needs_data`。播种日期只影响生育期解释：已有光学田况或未来低温过程仍以 `partial` 交付，不伪造作物阶段或风险等级。

任务 API 只提交分析目标、地块、公开任务时段、当前边界版本的采集批次和用户明确选择的现场记录。`AnalysisToolsetFactory` 在领域边界内统一计算种植季光学窗口、单日雷达对比扩窗和水氮支持窗口，筛选相关采集批次，并严格按 `CORN_SKILLS` 声明的顺序返回完整工具集。缺少或重复注册必要工具会在任务启动前失败；没有任何采集批次、当前时段没有数据，或长势/水氮任务缺少同一日期的完整 Sentinel-2 光谱与 SCL 资产时返回 `needs_data`，不启动模型，并列出对应能力的数据配置、缺失来源和“打开地块数据”行动。采集批次存在只说明做过采集，不等于数据已经达到分析工具的前置条件。

`needs_data` 行动同时携带后端生成的 `AnalysisNextAction.acquisitionRequest`。该计划冻结地块、边界版本、能力 profile 和时间窗口；前端点击后原样创建独立采集任务，不从自然语言反推来源。当前首条长势链路只执行 `analyze_optical_condition -> estimate_crop_stage -> assess_growth_status`，所以 `growth_stage_v1` 只补采 Sentinel-2；普通地块数据更新仍使用包含六类来源的 `field_baseline_v1`。Sentinel-1 长势融合属于后续 profile 升级，不作为当前链路已实现能力。

生产功能执行器使用确定性 Workflow：按当前目标固定工具集合和顺序，校验任务与地块 scope，并把运行状态、受控工具步骤、结果引用、最终摘要或失败原因写入 `agent_runs` / `agent_run_events`。`GET /api/v1/tasks/:id/agent-run` 只返回稳定的用户可复查轨迹，不暴露内部配置、密钥或供应商响应。模型不能改变工具顺序、结构化计算结果或质量门；正文生成契约以第 7 节为准。生成失败不把已形成计算结果的任务标记为计算失败。

每项 Workflow 在代码中声明工具顺序、最终业务工具及其最小前置证据。AI 文档生成成功时，任务摘要复用生成的 overview；失败时保留最终 `AnalysisResult` 的计算摘要。两者均不覆盖原始结构化结果。

任务内对话已经接入开源 Codex harness 与 PostgreSQL。`GET /api/v1/tasks/:id/conversation` 返回该任务的用户可见消息，`POST /api/v1/tasks/:id/messages` 围绕原任务结果继续提问。Codex 运行在独立空目录和只读沙箱中，关闭网络、搜索和审批式扩权；对话只读取结构化任务摘要、来源、限制、行动和最近消息，不注册遥感工具，不会重新采集、静默重跑分析或改变地块、时段和目标。消息成对写入 `task_conversation_messages`，模型失败时不留下半条会话。system prompt、密钥和供应商 payload 不进入消息表。

普通 Agent 对话与确定性工作流分离。`GET /api/v1/fields/:id/conversation` 和 `POST /api/v1/fields/:id/messages` 通过 Codex harness 进行正常对话并写入 `field_conversation_messages`；知识性问题可通过地块范围的 `search_agronomy_knowledge` 获取带出处的一般解释，但不会把知识写成当前地块事实，也不会创建分析任务。用户询问地块面积、种植档案、当前数据或最近任务时，服务端先用 `get_field_context` 读取当前地块，数据状态只聚合当前边界版本已登记的来源，并以普通对话文字返回。用户询问任务进度时，`get_workflow_status` 读取最新匹配任务；用户追问任务结果时，`get_task_result` 读取最新匹配任务，并按摘要、地图位置、判断依据、实际限制或下一步行动组织发布内容。结果查询不会越过更新的未完成任务去返回旧结论。这些查询不调用对话模型，不创建任务、采集或额外结果卡片。用户要求记录现场观察时，服务端返回 `record_scouting_note` 候选草稿但不写库；前端只显示简短摘要，要求用户在地块内选择位置、检查预填字段并确认保存。用户明确提出长势、水氮、积水或霜冻分析时，服务端返回三步 Workflow 计划、资料缺口和冻结的 `startRequest`；未确认时任务数不变，点击“确认并开始”后前端原样提交该请求并切换到“功能”面板。原始用户需求随任务保存，服务端按当前地块复核作物和范围。施氮方案仍位于水氮管理内部，不由对话计划自动生成。

“功能”使用单一总览界面，长势巡检、水氮管理、积水识别和霜冻预警四张卡同屏呈现。卡片只承担能力识别和进入，不持续占用工作流空间；点击后保留左侧功能总览，在右侧地图区域打开聚焦的任务弹窗，移动端使用贴底面板。弹窗提供任务目标、地块范围、时间和唯一的启动动作；确认后回到左侧任务面板运行，并通过明确的返回入口回到总览。水氮管理在同一功能域内保留“排查 / 施氮”二级切换，不把施氮拆成第五个一级功能。

功能 Workflow UI 遵循单一任务面板契约：能力名称和地块固定在面板头部，三种状态不更换视觉骨架。运行前只展示任务目的、任务特有的时间或事件范围和一个启动动作；运行中只展示当前阶段、进度和折叠的“过程”；运行后默认展示状态、`AnalysisBrief`、地图关注区和一个主要动作，详细来源、数据限制与工具轨迹统一进入“依据与数据”。四类 Workflow 复用视觉骨架，但拥有各自的输入语义、完成条件和解读规则，不展示内部工具链、重复结论或教学性说明。每个可见文字必须服务于判断、定位或行动。

首个真实地块已完成四项链路的初步验收：

- 长势监测：已返回 2026-06-26 光学状态、灌浆/拔节期估计、田内差异地图；只有单一可用光学时相时保持 `partial`，不生成虚假的变化趋势。
- 积水识别：已用 2026-07-23 / 2026-08-04 同轨 Sentinel-1 完成真实雷达对比；12 天间隔、99.5% 有效覆盖，发现约 9.96 公顷、占地块 10.87% 的显著变化区。同期历史天气只覆盖 54.5%，因此结果如实保持 `partial / radar_change_only`，只发布雷达变化和补数/核查行动，不把变化区称为疑似积水。
- 霜冻预警：当前真实 IFS 预报采集未成功，Workflow 返回 `needs_data` 和“暂时没有未来低温预报”，不发布最低温、风险等级或低洼关注结论。`high / watch / normal`、生育期敏感性和地形状态已由受控测试覆盖，但这些测试不能描述为真实地块风险验证。
- 水氮诊断：地块“田况”先按 OneSoil 式工作流直接提供日期、原图、指数、田内对比和季内时序；Agent 任务从用户选定日期发起原因排查。只有光学定位时，对用户交付“已定位，待巡田”：日期间全田均值变化和单期田内 NDVI 相对低值区分开表达，不能把后者称为变化区、水氮异常区或长期生产力分区。内部任务可保持 `partial`，但这不表示田况浏览失败。空间对齐雷达、强降雨与低洼组合或同期现场记录实际改变原因方向后，任务才升级为原因排查结果并纳入相应业务来源。没有本地验证模型时不确认缺氮、缺水，也不生成处方。

当前结果证明四类 Workflow 已能保存结构化事实并遵守质量门，也验证了积水和霜冻在证据不足时不会补造结论。仍需逐项补齐真实业务验收样本，特别是“达到 20 毫米关联事件且确有积水”“有效未来低温预报”“有水分独立支持”和“有氮素现场对照”样本，不能把受控测试、雷达单源变化或仅完成田内定位的结果当成模型效果结论。
