# 黑土农情 Agent 工具设计

> 本文是 Agent、Workflow 和工具边界的设计事实来源。结果字段和状态以 [ai-tool-contracts.md](ai-tool-contracts.md) 与 `packages/contracts/src/index.ts` 为准。

> 增量方案：需要设计跨期空间变化、现场证据复核、专业审核或持续预警时，读取[工具体系完整设计](farm-agent-tool-system-plan.md)。该文档定义待实施目标与分期验收，不改变本文所述当前十个工具的实现基线。

## 1. 设计结论

霜冻、水氮、积水和长势不是四个工具，而是四条面向用户的 Workflow。一次点击可以完成一条 Workflow，但内部必须保留每个步骤的执行状态、来源、质量和产物引用。

```text
用户目标
  -> 黑土农情 Agent（理解、补充、解释）
  -> 一个固定 Workflow（编排、质量门、停止条件）
  -> 多个受控步骤工具（读取、计算、判断）
  -> AnalysisResult + 地图/图表产物
  -> 结论、依据、限制和下一步行动
```

当前代码中的 `ControlledAnalysisTool` 表示“Workflow 步骤工具”，不是允许对话模型自由选择的工具市场。Workflow 由服务端根据 `CORN_SKILLS` 固定顺序调用；对话 Agent 不能改变顺序、传入路径或覆盖结果。

### 1.1 对话 Agent 的定位

对话 Agent 不是传统客服，也不是直接操作遥感工具的分析员。它是“农情任务入口 + 工作流协调者 + 结果解释助手”：可以理解用户意图、读取已有结果、生成执行计划，并在用户明确确认后启动一个高层 Workflow；Workflow 启动后由服务端执行固定步骤，结果回到对话中继续解释。

```text
自然语言问题
  -> 读取当前地块和已有结果
  -> plan_workflow（只规划，不执行）
  -> 用户确认
  -> start_workflow（只启动，不暴露底层步骤）
  -> get_workflow_status / get_task_result
  -> 正常对话解释结果
```

对话工具与 Workflow 步骤工具必须是两个接口。对话 Agent 可以使用的第一版门面工具为：

| 对话工具 | 用途 | 权限 |
| --- | --- | --- |
| `get_field_context` | 当前地块、作物、播种日期、最近任务和数据状态 | 只读，可自动调用 |
| `get_task_result` | 读取摘要、证据、地图发现、限制或下一步动作 | 只读，可自动调用 |
| `search_agronomy_knowledge` | 查询限定范围内的东北玉米农学知识 | 只读，可自动调用 |
| `plan_workflow` | 检查资料、生成工作流步骤和缺口 | 只读，可自动调用 |
| `start_workflow` | 按已确认的计划创建一次固定 Workflow 任务 | 有副作用，必须确认 |
| `get_workflow_status` | 读取任务进度、失败步骤和完成结果 | 只读，可自动调用 |
| `record_scouting_note` | 保存用户明确确认的现场观察 | 写入操作，必须确认 |

第一版对话 Agent 不直接注册 `analyze_optical_condition`、`analyze_radar_change`、`analyze_weather_event` 或任何业务判断工具。`get_field_context` 已将原先隐式传给模型的地块资料收敛为确定性只读门面：按当前边界版本读取地块档案、聚合数据状态和最近三项任务，不返回边界几何、不调用模型。`plan_workflow` 生成待确认计划，并冻结地块、作物、目标、时间口径和原始用户需求为 `startRequest`；未确认时不创建任务。用户点击确认后，`start_workflow` 原样提交该请求到现有任务入口，服务端再次按当前地块复核作物和任务范围。`search_agronomy_knowledge` 已同时接入任务对话和普通地块对话：任务范围按当前 Workflow 过滤来源，地块范围只允许已授权玉米地块并用于一般农学解释。`get_workflow_status` 已作为确定性只读门面接入：状态询问优先于结果与 Workflow 启动识别，只读取当前地块最新的匹配任务，不调用对话模型、不创建任务。`get_task_result` 读取当前地块最新匹配任务的已发布结果，分别回答摘要、地图位置、判断依据、实际限制和下一步行动；更新的未完成任务不会被更早的旧结果越过，查询返回 `found`、`not_ready` 或 `not_found`，并继续作为普通对话文字呈现。`record_scouting_note` 已接入“候选草稿 -> 地图位置 -> 表单确认 -> 保存”的受控写入流程：对话阶段只提取观察日期、墒情、叶色、病虫害和备注，不写库；缺少位置或坐标越界时必须在当前地块内重新点选，最终复用巡田表单确认保存。这些门面都独立于 `ControlledAnalysisTool`。

启动权限按风险分级：查询和解释自动执行；创建长势、水氮、积水或霜冻任务必须先展示计划并获得确认；保存巡田记录、进入施氮方案、提交专业复核或发布高风险动作需要二次确认。对话 Agent 只能启动预定义的 Workflow 枚举，不能传入任意代码、阈值、文件路径或工具顺序。

## 2. 四层职责

| 层 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| 用户 / 对话 Agent | 理解任务、选择功能、补充播种日期等资料、解释已经完成的结果 | 不计算指数、不选波段、不拼空间运算、不改任务状态 |
| Workflow | 固定步骤、依赖、分支、质量门、重试/停止、最终业务工具 | 不保存供应商 SDK 细节、不实现像元处理 |
| 受控工具 | 在服务端任务上下文内读取登记产物，完成一项稳定的观测、推断或判断 | 不下载外部数据、不接受任意路径/阈值/代码 |
| 内部空间与数据能力 | 坐标归一、裁剪、配准、重采样、统计、空间相交、GeoJSON/PNG 写入、缓存和恢复 | 不成为模型可调用的独立工具 |

工具内部可以使用很多函数和库，但 Agent 只看到注册在 Workflow 中的语义工具。`clip_raster`、`reproject`、`resample`、`intersect_layers`、`write_geojson` 和供应商 API 适配器都属于内部实现。

## 3. 用户能力与 Workflow

| 用户入口 | Workflow ID | 完成问题 | 最终工具 |
| --- | --- | --- | --- |
| 关键生育期长势监测 | `growth_stage_monitoring` | 当前处于什么阶段、长势如何、哪里需要看 | `assess_growth_status` |
| 水氮管理 / 诊断 | `water_nitrogen_diagnosis` | 哪些区域存在水分或养分相关线索、先去哪里核查 | `assess_water_nitrogen_evidence` |
| 水氮管理 / 施氮方案 | `variable_nitrogen_plan` | 如何把已有相对长势区转成待复核的候选施氮方案 | 领域服务，不进入四条 Agent 分析链路 |
| 农田积水灾害识别 | `waterlogging_detection` | 降雨后哪里疑似积水、影响多大、先核查哪里 | `detect_waterlogging` |
| 霜冻风险提前预警 | `frost_risk_warning` | 未来什么时间有风险、哪里需要重点防护 | `assess_frost_risk` |

Workflow 的统一输入是服务端绑定的 `taskId`。任务创建时冻结地块、边界版本、作物、时间窗口、数据批次和用户明确选择的现场记录；工具不从模型输入中重新推断这些范围。对话 Agent 只能通过确认后的 `start_workflow` 创建任务；确认按钮提交 `plan_workflow` 返回的同一份 `startRequest`，不能由前端重写目标、时段或用户需求，也不能静默触发或复用旧任务伪装成新结论。

## 4. Workflow 图

### 4.1 长势监测

```text
analyze_optical_condition -> estimate_crop_stage -> assess_growth_status
```

- 必需：至少一组合格光学观测和有效播种日期。
- 单期光学可以交付当前状态和田内差异，但必须为 `partial`，不能生成历史趋势。
- 终点只发布生育期、长势、变化日期、差异区和巡田动作，不发布产量或施肥处方。

### 4.2 水氮协同诊断

```text
analyze_optical_condition
  -> estimate_crop_stage
  -> analyze_radar_change
  -> analyze_weather_event
  -> analyze_terrain_susceptibility
  -> get_soil_background
  -> assess_water_nitrogen_evidence
```

- 光学负责定位田内差异；雷达、降雨、地形或明确选择的同期巡田记录提供独立支持。
- SoilGrids 只提供地块背景，不生成田内分区。
- 只有光学定位时仍可交付“已定位，待巡田”；不能把相对低值区命名为缺氮区或缺水区。
- 诊断完成后不能自动跳转施氮方案；施氮方案需要用户填写用量并进入 `needs_review`。

### 4.3 积水识别

```text
analyze_radar_change -> analyze_weather_event -> analyze_terrain_susceptibility -> detect_waterlogging
```

- 雷达必须具备同轨、同极化、可比较的前后时相；天气必须覆盖关联降雨过程。
- DEM 只用于易发性与巡查排序。
- 缺雷达基线、缺降雨关联和无地块覆盖分别返回独立缺口。
- 结果是疑似积水，不是只凭雷达确认的已发生灾害。

### 4.4 霜冻风险

```text
analyze_weather_event -> analyze_terrain_susceptibility -> estimate_crop_stage -> assess_frost_risk
```

- 天气工具必须选择带生成时间和有效期的最新低温预报。
- 生育期来自播种记录和版本化阶段规则；缺播种日期进入 `needs_input`。
- 地形只产生低洼关注背景，不把 0.25 度预报下推成田内精准温度。
- 结果是未来风险窗口和防护关注区；涉及防护措施时按风险等级进入专业复核。

## 5. 工具总目录

工具分为三类：

1. **观测工具**：从登记产物生成可复查的时空事实和地图/图表；
2. **上下文工具**：提供生育期、天气事件、地形和土壤背景；
3. **业务判断工具**：读取本次任务前序结果，形成用户可执行的任务结论。

业务判断工具只能读取当前任务的前序结果，不能自行访问供应商响应或历史任务产物。所有工具都返回 `AnalysisResult<T>`，包含状态、来源、质量、发现、产物、限制、下一步动作和错误语义。

## 6. 逐个工具设计

### 6.1 `analyze_optical_condition`

**定位**：光学观测工具；为长势和水氮 Workflow 提供统一的 Sentinel-2 田况事实。

**输入**：服务端绑定的 `taskId`、地块边界版本、任务时间范围、已登记 Sentinel-2 资产。

**内部处理**：按观测日期归并完整光谱和 SCL；统一分析网格；执行云、雪、坏像元和覆盖质量门；计算 NDVI、NDRE、RECI、MSAVI、NDMI、NDWI；计算相邻日期地块均值变化和最近日期的田内相对差异。

**输出**：当前观测、可用观测序列、日期变化、田内相对差异区、真实栅格图层和来源日期。

**完成条件**：两期以上可比日期为 `succeeded`；单期为 `partial`；无覆盖、全云或资产不完整为 `needs_data`；产物读取失败为 `failed`。

**不负责**：不确认缺氮、缺水、病虫害、产量或施肥量。

**复用**：`growth_stage_monitoring`、`water_nitrogen_diagnosis`，并为地块田况浏览提供历史可视化。

### 6.2 `estimate_crop_stage`

**定位**：作物上下文工具；把播种记录和参考观测日期转成阶段区间。

**输入**：地块作物、播种日期、品种（若有）、参考观测日期和版本化阶段配置。

**内部处理**：计算播后天数；按版本化阶段区间返回候选阶段和置信度；保留缺少积温/品种校准的限制。

**输出**：阶段、参考日期、播后天数、规则版本、置信度和限制。

**完成条件**：播种日期和参考日期有效为 `succeeded`；缺播种日期、日期无效或播种晚于观测日为 `needs_input`。

**不负责**：不凭单幅影像确认阶段，不修改播种记录，不把无效日期静默归零。

**复用**：长势、水氮、霜冻。积水识别不把阶段作为必要前置。

### 6.3 `assess_growth_status`

**定位**：长势 Workflow 的终点判断工具。

**输入**：当前任务已保存的光学结果和生育期结果。

**内部处理**：结合阶段上下文解释 NDVI 状态和变化；区分上升、稳定、下降和时相不足；组织田内相对低值/接近/高于均值区域；生成巡田动作。

**输出**：当前结论、生育期、有效观测数、最新有效覆盖、趋势、偏弱区面积与地块占比、来源日期、限制和巡田动作。偏弱区面积单位为公顷，按 `地块面积 × 偏弱区有效像元数 ÷ 地块总像元数` 计算；因此未通过质量门的像元不计入偏弱区，最新有效覆盖下降时，所有分区面积之和也会相应小于地块面积。偏弱区占比为 `偏弱区面积 ÷ 地块面积`。偏弱区只绑定生成该分区的最新观测日期，不能叠加到历史图层上。

**完成条件**：光学和阶段均可用时为 `succeeded`；单期、观测过期或最新覆盖受限时为 `partial`；缺阶段时保留光学结果并为 `partial`，同时给出补播期行动；缺光学时为 `needs_data`。存在偏弱区时进入分区核查，没有偏弱区时只提供常规代表性巡田记录，不创建不存在的异常核查对象。

**不负责**：不跨地块排名，不预测产量，不直接推荐肥料或灌溉。

**复用**：只属于长势 Workflow；其相对长势区可被施氮方案显式选择，但不会自动触发施氮。

### 6.4 `analyze_radar_change`

**定位**：雷达观测工具；提供单期后向散射和可比日期变化。

**输入**：任务地块、目标日期/时间窗口、已登记 Sentinel-1 资产。

**内部处理**：筛选同轨、同极化、相近空间覆盖的观测；统一分析网格；生成 VV、VH 和变化图层；计算有效覆盖和变化区。

**输出**：前后日期、轨道和极化匹配摘要、VV/VH 观测、变化区、图层产物和质量状态。

**完成条件**：有可比前后对为 `succeeded`；只有单期可返回单期观测但为 `partial`；无同轨基线、无覆盖或质量不足为 `needs_data`。

**不负责**：不把单期雷达称为积水或土壤湿度，不凭雷达单源生成灾害结论。

**复用**：积水 Workflow；水氮 Workflow 只在与光学日期满足窗口时作为独立水分线索。

### 6.5 `analyze_weather_event`

**定位**：天气上下文工具；把历史降雨或未来低温预报变成事件窗口。

**输入**：任务目标、固定时间窗口、地块位置、已登记 ERA5-Land 或 ECMWF IFS 产物。

**内部处理**：按任务选择历史或预报数据；按任务窗口过滤有效时间，计算历史小时覆盖率、预报时间覆盖率、累计降雨、相互分离的多次降雨过程、最低温和风险窗口；保留预报生成时间、有效期和空间尺度。

**输出**：事件类型、日期窗口、序列图表、窗口统计、来源日期、预报有效期和尺度限制。

**完成条件**：当前 Workflow 实际请求的数据角色达到 80% 时间覆盖率为 `succeeded`；部分日期可用或任一请求角色覆盖率不足 80% 为 `partial`；无窗口覆盖为 `needs_data`。只请求历史或只请求预报时，不因另一角色不存在而降级。

**不负责**：不生成田内天气栅格，不把天气事件直接写成积水或霜冻灾害。

**复用**：积水、水氮、霜冻。历史降雨和未来预报必须按角色区分。

### 6.6 `analyze_terrain_susceptibility`

**定位**：地形背景工具；生成低洼、坡度和相对高程等静态空间背景。

**输入**：地块边界版本和已登记 DEM 资产。

**内部处理**：统一坐标与分析网格；裁剪 DEM；计算高程、坡度、相对高程和低洼易发性；只有分区均值同时处于地块低分位且比地块均值低至少 0.5 米时才标记为低洼；输出覆盖和分辨率限制。

**输出**：地形统计、关注区、静态地图图层和质量信息。

**完成条件**：有覆盖且达到像元门槛为 `succeeded`；部分覆盖为 `partial`；无覆盖或产物不可读为 `needs_data`/`failed`。

**不负责**：不确认积水、不确认霜冻发生，不把静态易发性当成实时事件。

**复用**：积水、水氮、霜冻；只在它实际改变排序或解释时进入业务来源。

### 6.7 `get_soil_background`

**定位**：土壤背景工具；提供地块级 SoilGrids 属性和尺度限制。

**输入**：地块边界版本和已登记 SoilGrids 产物。

**内部处理**：读取 Q0.5 深度属性；按地块汇总；转换明确单位；记录 250 米分辨率和覆盖限制。

**输出**：地块级砂/粉/黏粒、有机碳等背景值、深度、单位、有效/总像元数、有效覆盖率、来源和限制。

**完成条件**：全部请求属性有合法地块背景且有效覆盖率达到 80% 为 `succeeded`；部分属性缺测或任一测量覆盖率低于 80% 但仍有可交付结果为 `partial`；全部数据不可用为 `needs_data`。

**不负责**：不生成田内施氮区、不确认缺氮、不替代土壤检测。

**复用**：水氮 Workflow；只有实际影响排查方向时才进入最终业务来源。

### 6.8 `assess_water_nitrogen_evidence`

**定位**：水氮任务的多源比较工具；把观测组织成可读取、可复算的数据，交给 Agent 解释。

**输入与输出**：只消费已登记成果和用户明确选择的现场记录。返回实际光谱偏差、面积、时间对齐、雷达/低洼几何交集和全部同期现场对照；不返回预设原因或巡田优先级。详细契约、阈值、状态、计算口径与最小样例统一见 [工具契约：水氮协同诊断](ai-tool-contracts.md#水氮协同诊断)。

**完成条件**：计算完成与农学原因确认分别表达。没有现场记录不阻止遥感结果交付；缺测不填零；已尝试的必要比较失败有明确状态。判断和文档由 Agent 基于持久化数据及知识原文完成，处方继续独立复核。

**复用**：只属于水氮诊断；变量施氮方案是独立用户工作流。

### 6.9 `detect_waterlogging`

**定位**：积水 Workflow 的终点判断工具。

**输入**：雷达变化、关联降雨和可选地形易发性结果。

**内部处理**：检查灾前/灾后雷达可比性；计算雷达有效覆盖、显著变化面积和地块占比；只把雷达区间内单次累计达到 20 毫米的降雨过程作为关联事件，并在事件与变化空间/时间相容时生成疑似区；只有完整 DEM 才用于低洼核查排序。

**输出**：雷达前后日期与间隔、有效覆盖、显著变化面积与占比、20 毫米降雨门槛、最强达标事件、疑似影响面积与占比、分区面积与占比、证据链、核查优先级和限制。

**完成条件**：雷达对和覆盖其间的连续降雨齐备为 `succeeded`；低于 20 毫米时保留实际降雨和雷达变化事实，但结果为 `not_detected`，不生成疑似影响区；有可比雷达变化但天气缺失或覆盖不足时为 `partial / radar_change_only`，明确不判定积水；缺少可比雷达对为 `needs_data`。地形缺失或部分覆盖不阻断，地形状态不满足 `succeeded` 时不得提升核查优先级，也不得使用“低洼区”行动措辞。

**不负责**：不把低洼区直接当积水区，不使用天气单独生成田内多边形。

**复用**：只属于积水 Workflow。

### 6.10 `assess_frost_risk`

**定位**：霜冻 Workflow 的终点判断工具，不是一个“一步完成全部事情”的黑盒 Agent 工具。

**输入**：最新低温预报、生育期和地形易发性结果。

**内部处理**：先校验预报生成时间、有效窗口和最大 240 小时提前量；按作物阶段和预报最低温/持续时间计算风险等级；仅在 DEM 可用时以低洼和相对地形背景形成关注区；保留预报批次、覆盖率、最近格点距离、地形可用状态和模型版本。

**输出**：未来风险窗口、风险等级、最低温与持续时间、生育期与敏感性、预报生成时间与覆盖率、最近格点距离、`available / limited / missing` 地形状态、低洼关注区面积与地块占比、触发依据、限制、下一步动作和复核状态。

**完成条件**：生成时间合法、提前量不超过 240 小时且覆盖率达到 80% 的预报、生育期和完整 DEM 齐备时为 `succeeded`；缺预报为 `needs_data`，不发布风险等级；有有效预报但缺播种日期/阶段时为 `partial / undetermined`，只发布低温过程；预报覆盖或 DEM 受限时为 `partial`。地形不可用时不得在行动文字中声称已定位低洼区。当前工具只发布风险与现场核查动作；未来若发布具体高风险防护处置，才进入 `needs_review`。

**不负责**：不确认霜冻已经发生，不生成田内精准温度，不绕过专业复核发布高风险处置。

**复用**：只属于霜冻 Workflow。

## 7. 统一工具契约

### 7.1 输入边界

工具只接收 `{ taskId }`。服务端通过任务 ID 读取地块、边界版本、作物、时间窗口、授权关系、筛选后的采集清单和前序结果。模型不能传入文件路径、供应商资产 ID、波段、坐标系、阈值、SQL 或代码。

### 7.2 结果边界

每次调用保存一个独立 `AnalysisResult`，至少保留：状态、工具版本、任务归属、结构化结果、来源日期与角色、finding 来源、地图/图表产物引用、限制、下一步动作和稳定错误码。`execution` 统一记录工具身份、地块与边界版本、工具时间窗口、采集批次/资产、前序结果、参数摘要和输入指纹；字段定义只以 `packages/contracts/src/index.ts` 为准。

工具不得用空数组或零值掩盖缺测。结论范围因质量下降时返回 `partial`，不能继续伪装成 `succeeded`。

### 7.3 执行边界

```text
任务创建 -> 固定 scope 和 Workflow
Workflow -> 按声明顺序调用步骤工具
工具 -> 读取登记产物并保存 AnalysisResult
质量门 -> 继续、降级、needs_input、needs_data 或 needs_review
终点工具 -> 生成唯一业务摘要
前端/对话 -> 读取结构化结果，不覆盖事实
```

同一任务的同一工具使用稳定结果 ID；相同 scope、输入版本和参数生成相同输入指纹，重放不会新增重复步骤。同一地块的历史任务产物不能偷偷混入当前任务。Runner 校验任务、工具身份和地块 scope；工具失败要说明已完成的步骤和缺失步骤，不能用静默 fallback 生成“成功”。

## 8. 不注册为 Agent 工具的能力

以下能力必须保留在数据采集、工具内部或前端：外部数据搜索/下载/缓存/许可检查；坐标系转换、几何修复、裁剪、重采样、云掩膜和像元计算；文件路径、供应商产品 ID、内部 result ID 和对象存储 URI；任意 SQL、Python、Shell、网络请求和模型自行拼接的阈值；地图缩放、图层显隐、回到地块和图例展示；变量施氮的剂量计算和正式农机处方发布。

## 9. 验收标准

1. 四条 Workflow 的顺序、必需前置和停止条件在代码中可定位。
2. 十个步骤工具各有唯一职责，没有两个工具都负责同一判断。
3. 每个工具都能说明输入来源、输出产物、质量状态和不负责事项。
4. 天气、土壤或静态地形不会被伪装成高分辨率田内事实。
5. 失败、缺测、部分证据和专业复核都能在 `AnalysisResult` 中重放。
6. 前端只展示当前任务的结果与证据，不复制工具内部算法。
7. 用户只需选择农田、任务和时段，不需要理解遥感指标、坐标系或工具调用。
